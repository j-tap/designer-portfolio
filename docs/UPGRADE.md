# План обновления: Strapi 5, Nuxt 4, Node 24

Ветка: `upgrade/strapi5-nuxt4`. Пуш в `main` сразу деплоит на прод (`.github/workflows/deploy.yml`),
поэтому работа идёт в ветке, а в `main` она попадает только после проверки и бэкапа на сервере
(см. «Выкатка»).

## Зачем

- **Node 20** снят с поддержки в апреле 2026, а Nuxt 4.6 его уже не поддерживает → **Node 24 LTS**.
- **Strapi 4** больше не получает обновлений безопасности → **Strapi 5**.
- **Nuxt 3** в режиме поддержки, модули (i18n, sitemap, pinia) выпускают новые версии только под Nuxt 4.
- Часть плагинов Strapi заброшена с 2022–2023 годов и под v5 не существует.

## Что меняется в бэкенде и чем заменяется

| Было (v4) | Под v5 | Решение |
|---|---|---|
| `strapi-plugin-transformer` (убирает `attributes`/`data`) | не нужен: ответ v5 и так плоский | удалить; верхний `data` остаётся, как и сейчас |
| `strapi-plugin-populate-deep` (`populate=deep`) | есть только сторонний плагин, который подставляет populate в обход проверки прав REST | свой middleware: `populate=deep` → объект populate по схеме, дальше штатная валидация Strapi |
| `strapi-plugin-slugify` | нет версии под v5 | поле `slug` → тип `uid` с `targetField: title` (генерация в админке встроена в Strapi); колонка та же, данные сохраняются |
| `strapi-blurhash` 1.x | 2.0 тянет нативный `canvas` и качает картинки по HTTP | своя реализация на `sharp` + `blurhash`; атрибут `blurhash` у файлов сохраняется, иначе синхронизация схемы удалит колонку с 695 готовыми хешами |
| `strapi-provider-email-smtp` (2022) | — | `@strapi/provider-email-nodemailer` с теми же настройками TLS |
| `@strapi/plugin-i18n`, `@strapi/plugin-email` | встроены в ядро | удалить из зависимостей |
| `@retikolo/drag-drop-content-types` 1.x | 2.x | обновить |
| `strapi-plugin-multi-select` 1.x | 2.x | обновить |
| `@strapi/plugin-color-picker` 4 | 5 | обновить |
| свой плагин `relations-select` | — | удалить: это заготовка с тестовым пунктом «TEST», ни одна схема его не использует |

Изменения в коде отзывов:

- В v5 больше нельзя загружать файлы вместе с созданием записи (`files.files` в multipart):
  файлы сначала загружаются через сервис upload, потом их id указываются в записи.
- `lifecycles.afterCreate` в v5 срабатывает и при публикации черновика (публикация создаёт
  новую строку) — письмо о новом отзыве приходило бы дважды. Письмо уходит из контроллера.
- `publicationState=live` → `status=published`.
- Связи (`developments`, `cooperations`) задаются по `documentId`; фронт отправляет `documentId`.
- Ссылка на отзыв в письме — по `documentId` (так устроены адреса в админке v5).

Миграцию данных (`document_id`, черновики/публикации, связи локалей) Strapi 5 выполняет сам при
первом запуске. Перед этим обязательна копия `backend/.tmp/data.db` и `backend/public/uploads`.

## Что меняется во фронтенде

- Nuxt 4: структура каталогов остаётся прежней (в корне `frontend/`, Nuxt 4 её поддерживает),
  правки под изменения `useAsyncData` (`getCachedData`, общие данные по ключу), `process.client` →
  `import.meta.client`, дубль `compatibilityDate` в `nuxt.config.js`.
- i18n 10: `iso` → `language`, файлы переводов переезжают в `i18n/locales`, путь к `vueI18n`
  считается от каталога `i18n/`, `lazy`/`vueI18nLoader` убраны.
- sitemap 9: проверить API `defineSitemapEventHandler`/`asSitemapUrl`.
- Запрос проектов в карте сайта: `populate[]=updatedAt` — в v5 это ошибка 400 (строгая проверка
  параметров), убрать.
- Форма отзывов: отправлять `documentId` у направлений.
- Удалить прямые зависимости `vite` и `unhead` (их приносит Nuxt нужных версий).

## Как проверяем, что ничего не сломалось

До начала работ на копии БД сняты эталоны текущей версии (Strapi 4 + Nuxt 3):

1. **API** — ответы Strapi на все запросы, которые делает фронт (105 запросов: каждая локаль,
   категория, проект, отзывы, контакты, запросы карты сайта).
2. **Страницы** — SSR-HTML 88 адресов: главная, портфолио, все категории и проекты в ru/en,
   отзывы, контакты, донат, визитка, robots.txt, карта сайта. Из HTML извлекаются заголовки,
   мета-теги, JSON-LD, ссылки, картинки и видимый текст.

После каждого этапа те же снимки делаются с новой версии и сравниваются с эталоном. Допустимые
отличия: новое поле `documentId`, служебные поля (`publishedAt`) и хеши сборки.
Отдельно проверяются вручную: админка (вход, редактирование, drag-drop сортировка, multi-select,
color picker, генерация slug, загрузка картинки → blurhash), отправка отзыва с файлами и письмо.

## Результаты проверки бэкенда

- Миграция копии БД Strapi 4 → 5 при первом запуске: меньше секунды, без ошибок.
  Blurhash сохранился у всех 695 файлов, черновики отзывов разложены на черновик + публикацию.
- API: 101 из 104 ответов совпадают с эталоном полностью (порядок, id, связи, blurhash,
  multi-select). Отличия только ожидаемые: новые поля `documentId`/`focalPoint`, пустые
  множественные медиа приходят как `[]` вместо `null` (фронт проверяет `.length` — безопасно)
  и 400 на `populate[]=updatedAt` в запросе карты сайта (правится во фронте, этап 4).
- Отзывы: без токена / слишком быстро / поддельный PNG — 400; валидный отзыв сохраняется
  черновиком с файлом в папке «API Uploads», blurhash считается, связи — на версии языка
  страницы, `publishedAt`/`createdBy` от клиента игнорируются; `status=draft` черновики
  не отдаёт; публикация из админки повторного письма не шлёт; ошибка SMTP не мешает сохранению.
- Админка: вход, списки, генерация slug из кириллицы (`Тестовый проект Ёжик` →
  `testovyj-proekt-yozhik`), проверка уникальности slug, сортировка drag-drop, настройки
  drag-drop перенеслись из v4. Письмо через nodemailer 10 уходит (проверено на локальном SMTP).

## Решения

- **Strapi 5.57.0, а не 5.58.0.** 5.58.0 вышел в день работ; Yarn 4.18 по умолчанию не ставит
  пакеты моложе суток (`npmMinimalAgeGate`), и это разумная защита от взломанных релизов.
  Исправления безопасности из 5.58 (axios 1.20, handlebars 4.7.10, sharp 0.35.5) подключены
  через `resolutions`. Переход на 5.58+ — обычным `yarn up` через неделю-другую.
- **Yarn 4.18**: install-скрипты сторонних пакетов выключены по умолчанию. Разрешены только
  нужные через `dependenciesMeta` (`better-sqlite3` — нативная сборка, `esbuild`, `@swc/core`).
- **Остаточные предупреждения `yarn npm audit`** (исправленных совместимых версий нет):
  `braces` через chokidar (вотчер файлов в `develop`), `react-router` 6 (админка Strapi требует
  именно v6), `stream-json` 1.x (перенос данных, выключен без `TRANSFER_TOKEN_SALT`), устаревшие
  `glob`/`rimraf`/`inflight`/`prebuild-install`/`@koa/router` внутри Strapi. Уйдут с обновлениями Strapi.

## Выкатка на прод

1. На сервере сделать бэкап (БД и загрузки — в bind-mount, в образ они не попадают):
   ```sh
   cd <проект>
   docker compose -f docker-compose.yml -f docker-compose.prod.yml -f docker-compose.traefik.yml stop strapi
   tar czf ~/backup-$(date +%F).tgz backend/.tmp backend/public/uploads .env
   ```
2. Влить ветку в `main` → GitHub Actions выполнит `git pull && make prod`.
3. При первом запуске Strapi 5 мигрирует БД (секунды для текущего объёма). Проверить логи:
   `docker compose ... logs -f strapi`.
4. Проверить сайт и админку по списку из раздела «Как проверяем».

**Откат:** `git revert` мерж-коммита (или `git reset` на сервере на предыдущий коммит), восстановить
`backend/.tmp` из архива, `make prod`. Восстановление БД обязательно: Strapi 4 не умеет читать
базу, мигрированную Strapi 5.
